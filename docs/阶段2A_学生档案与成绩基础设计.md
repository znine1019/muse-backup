# 阶段2-A｜学生完整档案与训练数据基础设计

**状态：本地代码完成，云端结构未创建。**  
本阶段不自动执行 CloudBase 集合、索引或权限变更。

## 1. 目标

1. 扩展学生体育档案：专项、兼项、训练经历、训练年限、体考目标和身体历史。
2. 建立学生自报PB、教练审核、正式认可成绩的分层数据模型。
3. 为后续成绩排行榜和训练统计保留扩展能力。
4. 保持阶段1用户、角色、训练组和注册审核数据兼容。

## 2. 现有集合扩展

### student_profiles

保留现有注册字段，新增：

| 字段 | 类型 | 说明 |
|---|---|---|
| `primaryEventCode` / `primaryEventName` | string | 主项代码和名称 |
| `secondaryEventCodes` | string[] | 兼项代码，最多3项 |

现有 `heightCm`、`weightKg` 保留为兼容字段，并在新增身体记录时同步为最新值。

## 3. 新增集合建议

### body_measurements

| 字段 | 类型 | 说明 |
|---|---|---|
| `_id` | string | 确定性身体记录ID |
| `userId` | string | 学生用户ID |
| `heightCm` / `weightKg` | number | 身高和体重 |
| `measuredAt` | date | 测量日期 |
| `source` | string | 当前为 `student_report` |
| `submittedBy` | string | 提交学生用户ID |
| `createdAt` | date | 创建时间 |
| `schemaVersion` | number | 当前为1 |

建议索引：

- 普通复合索引：`userId: 1, measuredAt: -1`
- 不新增业务唯一索引；重复提交由确定性文档ID保证幂等。

### performance_records

| 字段 | 类型 | 说明 |
|---|---|---|
| `_id` | string | 确定性成绩记录ID |
| `studentUserId` | string | 学生用户ID |
| `eventCode` / `eventName` | string | 体育项目代码和名称 |
| `value` | number | 成绩数值 |
| `unit` | string | 秒、米等 |
| `comparison` | string | `lower` 或 `higher` |
| `achievedAt` | date | 成绩取得日期 |
| `source` | string | 当前为 `student_report` |
| `submittedBy` | string | 提交学生用户ID |
| `status` | string | `pending`、`approved`、`rejected` |
| `reviewedBy` | string | 审核教练或开发者用户ID |
| `reviewedAt` | date | 审核时间 |
| `reviewComment` | string | 审核意见 |
| `createdAt` / `updatedAt` | date | 创建和最后更新时间 |
| `schemaVersion` | number | 当前为1 |

建议索引：

- 普通复合索引：`studentUserId: 1, eventCode: 1, achievedAt: -1`
- 审核队列索引：`status: 1, createdAt: -1`
- 不新增唯一索引；同一学生同一项目可以保留多次测试记录。
- 确定性 `_id` 防止同一学生、项目、日期和成绩值的重复双击提交。

## 4. 项目与比较规则

项目规则集中配置在 `cloudfunctions/api/lib/performance-events.js`，服务端决定单位、范围及排名方向：

- 计时项目：`comparison=lower`，例如100米、200米、400米、800米、1500米。
- 远度项目：`comparison=higher`，例如跳远、铅球。
- 高度项目：`comparison=higher`，例如跳高。

前端只能选择服务端返回的 `eventCode`，不能自行提交单位或比较方向。

## 5. 成绩审核状态

- `pending`：学生申报后进入待审核，不能进入正式成绩或排行榜。
- `approved`：教练或开发者审核通过，可作为正式成绩和后续排行榜数据。
- `rejected`：保留原始申报、审核人和审核意见，但不得覆盖历史正式成绩。

审核操作记录审计日志：

- `performance.submitted`
- `admin.performance.approved`
- `admin.performance.rejected`
- `profile.updated`
- `profile.measurement_recorded`

## 6. 权限规则

- `profile.get` 只返回调用者本人档案。
- `profile.update`、`profile.add_measurement` 仅允许已激活学生更新本人数据。
- `performance.submit` 仅允许已激活学生提交本人成绩。
- `admin.list_student_profiles` 和 `admin.get_student_profile` 仅允许教练和开发者。
- 教练只能访问与本人负责训练组存在有效 `group_memberships` 的学生。
- `admin.review_performance` 开发者可审核全部；教练只能审核本人负责训练组内学生。
- 学生不能审核自己的成绩，也不能修改审核状态。
- 所有集合继续保持客户端不可直接读写，统一通过 `api` 云函数访问。

## 7. 后续排行榜扩展

排行榜查询只使用 `status=approved` 的成绩：

1. 按 `eventCode` 分组。
2. 根据项目规则选择升序或降序。
3. 按性别、周期和训练组生成分榜。
4. 再按学生维度选择历史最好成绩。

未审核的学生申报成绩不得进入排行榜。

## 8. 云端实施前提

在创建 `body_measurements` 和 `performance_records` 前，需要用户确认：

- 集合名称和字段结构。
- 两项建议索引。
- 两个集合继续设置为仅管理员可读写。
- 先创建集合和索引，再部署引用新集合的 `api` 版本。

未经确认不得直接在云环境创建集合、索引或修改权限。
