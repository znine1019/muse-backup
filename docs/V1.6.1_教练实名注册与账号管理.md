# V1.6.1 教练实名注册与账号管理

## 目标

解决：

- 教练无法填写真实姓名。
- 开发者账号列表无法识别教练。
- 无姓名账号缺少筛选和统一提示。
- 普通 `admin.assign_role` 可绕过教练实名资料直接授予 coach。
- 学生、家长、教练注册页对真实姓名的提示不统一。

## 数据模型

新增集合：

上线前需由项目所有者另行批准在目标环境创建 `coach_profiles` 集合及必要索引，并审核云函数部署包。本轮未修改任何真实 CloudBase 资源。

`coach_profiles`

字段：

- `_id`：`deterministicId('coach_profile', userId)`
- `userId`
- `name`
- `identityNote`
- `reviewStatus`：`pending | approved | rejected`
- `reviewComment`
- `currentReviewId`
- `submittedAt`
- `reviewedBy`
- `reviewedAt`
- `source`：`self_registration | legacy_backfill`
- `submissionCount`：同一账号的实名资料提交次数，用于生成稳定且不重复的审核记录标识
- `createdAt`
- `updatedAt`
- `schemaVersion`

沿用：

- `users`
- `registration_reviews`
- `role_bindings`
- `audit_logs`

不建立第二套用户或角色体系。

## 注册流程
## 全角色真实姓名规范

学生、家长、教练注册页统一在姓名输入区上方展示真实姓名提醒，并要求：

- 填写本人真实姓名。
- 禁止微信昵称、网名、虚假姓名或他人姓名。
- 家长不得填写孩子姓名。
- 姓名首尾空格自动去除。
- 空值和纯空格前端拒绝提交。
- 后端继续执行必填、去空格和 40 字符上限校验。

该规范不包含身份证号、人脸识别或第三方实名认证。


1. 用户在待审核页选择“教练员注册”。
2. `coach.submit_profile` 保存实名资料。
3. 新教练账号进入 `pending_review`，不直接获得 coach。
4. `registration_reviews` 写入 `profileType=coach`。
5. 开发者审核通过后：
   - `coach_profiles.reviewStatus=approved`
   - `users.status=active`
   - users 增加 coach
   - `role_bindings` 增加 active coach
   - 写 `admin.registration.approved`
6. 审核驳回时无其它角色的账号进入 `rejected`，可重新提交。

同一账号已有待审教练资料时，重复提交返回 `REVIEW_ALREADY_PENDING`；已有其它身份待审注册时返回 `REGISTRATION_ALREADY_PENDING`，避免同一账号并行生成多套待审申请。

## 历史教练补资料

历史已开通 coach 但无 `coach_profiles` 时：

- 仍保持 active/coach。
- 教练工作台显示“完善实名资料”。
- 用户提交资料后 source=`legacy_backfill`。
- 审核期间不撤销原 coach 权限。
- 审核通过后资料 approved，权限不变。
- 已有效的 coach `role_bindings` 保留原 `grantedBy/grantedAt`，不会因补实名审核被重写来源。

## 角色授予限制

`admin.assign_role` 授予 coach 前必须存在 approved `coach_profiles`。

否则返回：

`COACH_REGISTRATION_APPROVAL_REQUIRED`

该限制阻止：

- pending 账号无姓名直接开通 coach。
- 开发者通过普通角色按钮绕过教练实名审核。

撤销 coach 仍保留原逻辑；现有合法 coach 不会被自动撤权。

## 开发者账号列表

服务端 `admin.list_users` 同时读取：

- student_profiles
- parent_profiles
- coach_profiles

姓名选择优先级：

1. 当前或待审 coach 资料
2. 当前或待审 parent 资料
3. student 资料

无任何姓名时统一返回：

`未完善真实姓名`

永远不使用微信昵称或 OpenID 作为已验证真实姓名。

账号列表支持筛选：

- 有姓名 / 无姓名
- 当前或申请角色
- 账号状态
- 最近 7 / 30 天

列表显示：

- 姓名
- 申请角色
- 当前角色
- 首次登录时间
- 账号状态
- 审核状态

## 审计

新增：

`coach.profile.submitted`

教练审核沿用：

`admin.registration.approved`
`admin.registration.rejected`

审计 metadata 明确 `profileType=coach`。

每次重新提交后的审核审计按对应 `currentReviewId` 独立保存，不会覆盖上一轮驳回或通过记录。

## 删除账号

HOTFIX-01 第二轮新增受控逻辑删除：

- 仅 active developer 可调用。
- 开发者不能删除自己，任何有效 developer 均受保护。
- 删除前读取并返回全部业务关联统计，存在关联时必须由前端二次确认。
- 服务端要求一次性确认参数 `DELETE_ACCOUNT`。
- `users.status=deleted`、清空角色，并撤销活动 role binding、group membership 和 parent link。
- 待审 profile 与 registration review 终止，历史成绩、考勤、计划、反馈等文档保留。
- 已删除 users 文档继续保留，确定性 userId 不会在微信登录时静默重建。
- 重复删除返回幂等结果，不重复写审计。
- 逻辑删除不等同于个人信息物理清除。

新增审计：`admin.user.deleted`。

## 删除训练组

- 删除前统计成员、学生申请、注册审核、成绩、计划、考勤、请假、反馈、赛事和通知关联。
- 任一业务关联存在时返回 `TRAINING_GROUP_HAS_ASSOCIATIONS`，不修改数据。
- 无业务关联时执行安全归档：`status=deleted`、`enabled=false`，保留训练组文档。
- 已归档训练组不进入正常列表、选择器、统计或业务写入范围。
- 同名同周期创建请求不会通过原确定性 ID 静默恢复已删除训练组。
- 重复删除幂等，审计事件为 `admin.training_group.deleted`。
