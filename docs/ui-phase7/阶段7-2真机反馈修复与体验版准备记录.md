## 1. 问题一：developer 无法进入教练工作台

### 1.1 检查结论

| 检查项 | 结论 |
|---|---|
| coach 工作台路径 | `pages/coach/coach`（已在 `app.json` 注册） |
| 页面角色判断 | `pages/coach/coach.js` 允许 `coach` **或** `developer`：`sessionHasRole(session,'coach') \|\| sessionHasRole(session,'developer')` |
| 服务端权限 | 教练工作台调用的接口走 `loadManageActor`，服务端同样接受 `coach` 与 `developer`，**developer 天然拥有合法访问权限** |
| 现有路由与返回 | 从开发者工作台进入教练工作台应使用 `navigateTo`，返回时由原生返回按钮回到开发者工作台 |

**因此 developer 访问教练工作台是既有合法权限，无需授予任何新角色。** 真正缺失的只是"开发者工作台没有入口"。

### 1.2 实现

- 在开发者工作台的「全局管理入口」列表**首位**新增入口：**「查看教练工作台」**（`bindtap="goCoachWorkbench"`）。
- 处理函数：
  ```js
  goCoachWorkbench() {
    this.markNeedsRefresh();                      // 返回时强制静默刷新开发者工作台
    wx.navigateTo({ url: '/pages/coach/coach' }); // 压栈，返回即回到开发者工作台
  }
  ```
- **未新建页面、未授予 coach 角色、未修改 developer 身份、未伪造 OpenID、未绕过服务端权限**：该入口只做页面跳转，函数体内不包含 `assignRole` / `setGroupCoach` / `setUserStatus` 调用（已由结构校验与单元测试断言）。
- 返回流程：`navigateTo` 压栈 → 教练工作台使用原生返回 → 回到开发者工作台并触发静默刷新（不出现空白）。

## 2. 问题二：返回工作台时约 1 秒的数据空白

### 2.1 真实根因（已定位，非网络问题）

阶段7-2 首个版本的工作台实现存在两个问题：

1. **`onShow` 无条件执行完整初始化**
   从小程序其它业务页面返回工作台时（`navigateTo` → `navigateBack`），页面会触发 `onShow`；原实现里 `onShow()` 直接调用 `loadPage()`，对**所有区块重新发起全部接口请求**（学生 4 个、教练 7 个、开发者 6 个）。返回一次就多一轮 4—7 次云函数调用。

2. **加载状态被当作唯一的渲染开关（核心原因）**
   `loadPage()` 一进入就把所有区块状态置为 `loading: true`：
   ```js
   profileState: { loading: true, error: '' }, todayState: { loading: true, error: '' }, ...
   ```
   而模板用 `wx:if="{{todayState.loading}}"` 渲染骨架屏分支。**数据其实仍在页面内存里，但被骨架屏分支遮住了** —— 于是出现"数据短暂消失约 1 秒后重新出现"的现象。

   这 1 秒主要由云函数调用往返决定（多接口并行 + 可能冷启动），所以看起来像"网络慢"，实际是**本地状态机把已有数据主动隐藏了**，并且**重复拉取了已有数据**。

3. 附带问题：原实现缺少"身份与缓存绑定"、"并发合并"、"旧请求丢弃"等保护，多次快速返回可能产生重复请求。

### 2.2 修复方案：stale-while-revalidate（先用旧数据，再静默更新）

新增轻量控制器 `miniprogram/utils/workbench-controller.js`（无任何第三方依赖）：

| 能力 | 说明 |
|---|---|
| 会话内内存缓存 | 直接复用**页面实例的 `data`**，不做本地持久化存储；退出登录或 `reLaunch` 后页面销毁，缓存自然消失 |
| `MIN_AUTO_REFRESH_MS = 15000` | 返回工作台时若距上次成功加载不足 15 秒且不是从业务页面返回，则**直接跳过网络请求**，复用已有状态 |
| `SESSION_REVALIDATE_MS = 60000` | 会话（角色/状态）每 60 秒强制复核一次；日常数据请求本身也会在权限失效时返回错误，作为即时兜底 |
| 请求去重 | 同一区块同一时刻只发一个请求，重复调用复用同一 Promise |
| 竞态保护 | 每个区块有请求序号 + 会话代次（generation）：**缓存失效后到达的旧响应一律丢弃**，不回填页面 |
| `setIfChanged` | 只在值真正变化时 `setData`，减少无意义渲染抖动 |

三个工作台的状态机改为：

```
首次进入（页面无数据）  → 显示骨架屏 → 加载成功 → hasData=true、区块 ready=true
返回工作台（已有数据）  → 立即保留全部内容 → 顶部显示「正在刷新…」→ 后台静默刷新 → 只更新变化的区块
下拉刷新               → 保留已有内容 → 顶部显示「正在刷新…」→ 完成后更新
单区块失败             → 保留该区块上次成功数据 + 其它区块正常 → 顶部提示「部分数据更新失败，当前显示的是上次成功加载的数据」
权限失效               → 立即清空页面数据 → 跳转到会话对应入口
```

**模板层双保险**：区块骨架屏条件从 `加载中` 改为 `加载中 && 该区块尚未就绪`（`!xxxState.ready`），因此即使未来某条代码路径误将 `loading` 置真，**已有数据也不会被骨架屏遮住**。

### 2.3 行为矩阵

| 场景 | 期望行为 | 实现结果 |
|---|---|---|
| 首次进入（无缓存） | 允许骨架屏，不得白屏无反馈 | 骨架屏 + 区块独立加载 |
| 返回工作台（有数据） | 立即保留内容，后台刷新 | 保留 + `refreshing` 轻量状态，不进入骨架屏 |
| 返回工作台且 15 秒内 | 不重复请求 | 直接复用，无请求 |
| 从签到/申报/审批等业务页返回 | 强制刷新相关数据 | `markNeedsRefresh()` → 强制静默刷新 |
| 主动下拉刷新 | 保留内容 + 轻量刷新状态 | 保留 + 完成后 `stopPullDownRefresh` |
| 局部接口失败 | 不清空其它区块 | 保留旧数据 + 顶部"上次成功加载"提示 + 该区块错误与重试 |
| 全部接口失败（首次） | 显示错误与重试，不伪装成功 | 区块错误态 + `hasData` 保持 false |
| 账号停用/未审核/无角色 | 不得继续展示敏感数据 | 立即清空 + 跳转会话入口 |
| 退出登录 | 清理会话相关缓存 | `clearCachedData()` + `clearSession()` + `reLaunch` |

### 2.4 数据新鲜度提示（不把过期数据当实时数据）

- 静默刷新进行中显示 **「正在刷新…」**。

## 3. 缓存与失效规则（安全要求逐条落实）

| 要求 | 落实方式 |
|---|---|
| 1. 缓存与登录身份绑定 | 缓存即页面实例内存；每次进入用 **会话指纹** `用户ID#账号状态#角色集合` 校验 |
| 2. 角色变化清理缓存 | 指纹变化 → 立即 `clearCachedData()` 再重新加载 |
| 3. 账号停用使缓存失效 | 服务端返回 `ACCOUNT_DISABLED` / `ACCOUNT_NOT_ACTIVE` → 清空 + 跳转 |
| 4. 退出登录清理缓存 | `goHome()` → `clearCachedData()` + 控制器 `reset()` + `clearSession()` |
| 5. 不同微信账号不共享敏感缓存 | 页面实例随 `reLaunch` 销毁；且指纹不同即清空，不会复用他人数据 |
| 6. 不把其他学生数据留给新用户 | 同上；学生端只读取本人数据，工作台不缓存他人明细 |
| 7. 不能通过缓存绕过服务端权限 | 缓存只影响**渲染**，所有读取仍走云函数鉴权；权限失效时立即清空 |
| 8. 审批/修改后刷新待办 | 进入审批、成绩审核、反馈评价、赛事办理、考勤、签到、申报等页面前调用 `markNeedsRefresh()` |
| 9. 权限失效不继续展示敏感数据 | `handlePermissionLost()`：先清空数据，再跳转；本轮还修复了"其它区块在权限失效后继续回填"的边界问题 |
| 10. 不缓存 GPS 坐标等敏感资料 | 工作台不读取、不存储 GPS 坐标；教练端只缓存场次名称、半径、时间窗口等必要信息 |
| 额外 | **不做任何本地持久化缓存**（未使用 `wx.setStorage` 保存业务数据），仅复用同一会话的页面内存 |

> 注：`app.js` 原有的 `SESSION_CACHE_KEY` 仅保存登录会话对象（阶段1既有实现，未改动），不保存任何业务数据。

## 4. 两位领导的体验版接入准备

### 4.1 登录与注册链路核查（现状，未改动）

| 环节 | 现状 | 结论 |
|---|---|---|
| 微信一键登录 | `pages/index` → `auth.login` → 首次登录创建 `pending_profile` 账号 | 体验版可正常使用 |
| 首次注册 | `pages/register` 填写学生档案 → `profile.submit` → `pending_review` | 新微信号会被引导进入注册流程 |
| 注册审核 | 教练可审核本人负责训练组的申请，开发者可全局审核；均在页面内二次确认 | 默认无自动通过路径 |
| 角色授权 | 仅开发者可 `admin.assign_role`；前端不硬编码任何 developer 授权 | 新账号不会自动获得 developer |
| 教练范围 | `admin.set_group_coach` 配置教练↔训练组；服务端按范围过滤数据 | 教练只能查看授权训练组数据 |
| developer / bootstrap | 代码未改动；`LAST_DEVELOPER`（不能撤销最后一个开发者）保护仍在服务端 | 保持不变 |

### 4.2 建议的接入流程（4 步）

1. **领导扫码进入体验版** → 微信一键登录 → 自动创建 `pending_profile` 账号（此时无任何角色能力）。
2. **领导按引导填写注册资料**（姓名、性别、出生日期、身高体重、主项等）→ 提交 → 账号进入 `pending_review`，页面停留在"审核中"。
3. **开发者审核注册**（开发者工作台 → 待处理事项 → 通过）。通过后该账号获得 `student` 角色并变为 `active`。
4. **开发者授予教练权限**：
   - 开发者工作台 → 账号与角色 → 展开管理 → 为该账号「授予教练员」；
   - 开发者工作台 → 训练组与教练范围 → 展开管理 → 选择该教练 + 目标训练组 → 「启用范围」。
   - 之后领导重新进入小程序：若同时拥有学生+教练两个角色，会进入「选择身份」页 → 选择"教练端"进入教练工作台。
5. **（推荐）最小权限收尾**：若该领导只需要查看教练视角，可在账号与角色中**撤销"学生"角色**，只保留 `coach` + 训练组范围 —— 这样再次进入会直接到教练工作台，且不再看到学生个人数据入口。

### 4.3 最小权限建议

| 角色 | 是否授予 | 理由 |
|---|---|---|
| developer | **不授予** | 全局管理权限，仅所有者保留 |
| coach | 授予 | 领导查看训练组、考勤、成绩、统计所需 |
| student | 可保留（注册流程默认产生）或撤销 | 仅查看教练端时建议撤销，减少身份选择步骤与数据面 |
| 训练组范围 | 按需分配 | 教练仅能查看被授权训练组的数据，建议先只分配需要查看的组 |

### 4.7 本轮可能涉及真实数据写入的风险（体验版使用时请注意）

体验版连接的是**同一个云环境**，以下操作会写入真实数据：

1. 领导完成注册并提交档案 → 写入 `users` / `student_profiles`（真实姓名与身体数据）。
2. 开发者通过注册审核 → 写入用户状态与角色绑定 + 审计日志。
3. 授予教练角色 / 分配训练组范围 → 写入角色绑定与教练范围 + 审计日志。
4. 教练在工作台点「通过/驳回」注册审核、审批请假、审核成绩、评价反馈 → 均写入真实业务集合（**每步都有二次确认弹窗**）。
5. 若领导测试签到（GPS）→ 会写入考勤记录，并请求定位权限。

**建议**：体验期间优先只做"查看类"验证；需要验证写入时，明确告知领导哪些操作会产生真实记录。本轮未创建任何测试账号、未写入任何模拟成绩/考勤/训练组。
