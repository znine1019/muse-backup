## 2. 当前 UI/UX 主要问题（按根因归类）

项目所有者确认的 20 项问题，按根因归类后指向 6 个结构性原因：

### 原因 A｜缺少设计系统，只有一套通用样式
"白色卡片和按钮样式过于重复""有效信息密度偏低""不同业务页面缺乏差异化布局"都源于此。所有页面共用 `.card + .button-primary` 组合，导致：数据统计页、表单页、列表页长得一样，无法通过视觉结构表达"这是驾驶舱 / 这是编辑器 / 这是收件箱"。

### 原因 B｜工作台没有信息架构，只有按钮堆叠
- developer 工作台 8 个功能按钮纵向堆叠，无分组、无待办、无数据概览。
- coach 工作台 7 个按钮平铺，未区分"今天必须做的"和"偶尔用的"。
- student 首页 11 个按钮挤在两张卡片里，最重要的"今天要不要签到"反而不突出。
- 三类角色首页都缺少信息层级，没有"当前最重要 → 常用 → 其余"的次序。

### 原因 C｜页面顶部是"文档腔"，不是"产品腔"
每个页面都是 `brand(英文模块名) + 大标题 + 一段长说明`。这直接造成：重复英文模块名（COACH / ATTENDANCE / STUDENT / STATISTICS…）、大标题与说明占用首屏、developer 访问共享页面时看到"COACH"字样（因为页面文案写死为教练视角）。
黄色技术提示（`.notice`）被大量用于解释"权限由云函数校验""前端不决定数据范围"——这些是开发期说明，对使用者无价值，却占据了首屏。

### 原因 D｜高频表单按"字段全暴露"设计，没有按场景收敛
- GPS 考勤要求手输经纬度（把工具测量的活交给教练），且半径/精度/时间窗口无字段说明。
- 训练计划编辑把 8 个参数一次性平铺，短跑和力量训练看不到各自的核心参数。
- 赛事创建 5 类信息混在一个长表单里，参赛项目复选框拥挤、组别靠手动输入逗号分隔文本。

### 原因 E｜数据呈现停留在"文本卡片"，没有数据可视化语言
统计工作台整页是文本卡片堆叠：数字与标签同级、无趋势、无对比、无排行榜表现力。现有 Canvas 图表（`trend-chart`）只在报告页复用，没有形成统计页的图表体系。

### 原因 F｜通知与反馈缺少"注意力分配"
通知管理不区分重要与普通；训练反馈页把"需要关注的学生"和普通记录混在同一列表中，教练需要逐条读才能发现风险。

## 3. 三类角色使用场景（阶段7的设计依据）

### 3.1 学生（100—300 人，使用频率最高、单次时长最短）

| 场景 | 频率 | 关键诉求 | 设计含义 |
|---|---|---|---|
| 查看今天要不要训练、在哪、几点 | 每次打开（每日 1—3 次） | 3 秒内得到答案 | 首屏必须有"今日训练 + 签到入口" |
| 到场签到 | 每次训练 | 操作越少越好 | 签到入口固定、一步可达 |
| 填报训练反馈 | 每次训练后 | 快、可跳过 | 与签到场次绑定，2—3 个字段 |
| 查看自己的成绩/PB/排名 | 每周 | 看到进步 | PB 与趋势是核心情绪价值 |
| 请假 | 偶发 | 状态可见 | 入口易找、审批结果可见 |
| 赛事意向报名 | 赛季性 | 便捷、可撤销 | 多项目勾选 + 教练外部报名说明 |
| 看通知 | 每周 | 重要通知不漏 | 重要置顶 + 未读角标 |

**结论**：学生端设计目标是**降低认知负担与操作步数**，同时用"进步可视化"提升长期使用率。

### 3.2 教练（5—10 人，单次时长长、连续操作多）

| 场景 | 频率 | 关键诉求 | 设计含义 |
|---|---|---|---|
| 看今天要做什么 | 每日（早/训练前） | 待办集中 | 工作台首屏 = 待办队列 + 今日考勤状态 |
| 建考勤场次 | 每次训练前 | 别让我填坐标 | 地图选点、参数有默认值 |
| 审批请假 / 审核成绩 / 核实考勤 | 每日多条 | 批量、行内处理 | 列表行内操作，减少跳转 |
| 写训练计划 | 每周 1—3 次 | 按专项填核心参数 | 表单按训练类型收敛字段 |
| 发布通知 / 赛事 | 每周/赛季 | 一次填完、可复用 | 分组表单 + 草稿 |
| 导出发给办公室 | 每月 | 一步导出 | 统计页直接导出 |
| 看谁需要关注 | 每周 | 主动发现风险 | 反馈页优先展示"需关注学生" |

**结论**：教练端设计目标是**减少操作步骤与重复输入**，把"待办"作为一等公民。

### 3.3 developer（1 人 + 少量授权）

| 场景 | 频率 | 关键诉求 | 设计含义 |
|---|---|---|---|
| 审核注册、授权角色 | 新增学员时 | 权限范围清楚 | 授权前后影响范围明确提示 |
| 查看系统与数据状态 | 每周 | 一屏掌握 | 环境/集合/账号/审计的状态条 |
| 全局成绩审核与统计 | 月度 | 全局视角 | 与教练端同构 + 全局范围标识 |
| 排查问题、看审计 | 偶发 | 可追溯 | 审计入口明确，但不需要首屏大按钮 |
| 维护训练组与教练范围 | 学期性 | 变更安全 | 变更前确认、保留历史 |

**结论**：developer 端设计目标是**结构化分组 + 待办 + 状态可视化**，把"8 个平铺按钮"改为 3—4 个职责分组。

## 4. 设计系统基线（三套方案共同遵守）

以下规范同时适用于 A1/A2/A3，方案差异体现在"取值与表现方式"，不体现在"规范有无"。

### 4.1 颜色与层级（共 4 层语义）

| 层级 | 用途 | 说明 |
|---|---|---|
| 品牌层 | 主品牌色 + 其浅色底 | 深蓝作为品牌主色保留；A1 使用深蓝+青/黄绿，A2 使用乔格蓝+能量橙，A3 使用单一蓝+数据色 |
| 语义层 | 成功 / 警示 / 危险 / 中性 | 成功=出勤与通过，警示=待处理与迟到，危险=驳回与异常 |
| 数据层 | 图表序列色 | 主序列、对比序列、当前高亮序列，最多 3 色 |
| 表面层 | 页面底 / 卡片 / 分隔线 / 遮罩 | 决定信息密度与层级感 |

**约束**：不使用纯色单一色调铺满整个界面；强调色只用于"需要被点或被比较"的元素；同一屏内强调色不超过 2 种。

### 4.2 文字层级（6 级）

| 级别 | 用途 | 相对字号 |
|---|---|---|
| 数值级 | PB、比分、大指标 | 最大，等宽/等宽数字字体 |
| 页面标题 | 当前页面/对象名 | 大 |
| 区块标题 | 卡片与分组标题 | 中 |
| 正文/列表主文 | 名称、条目 | 中 |
| 次要说明 | 时间、范围、状态 | 小 |
| 微标签 | 单位、字段提示 | 最小 |

**规则**：所有数字使用等宽数字（`font-variant-numeric: tabular-nums`），保证数字列对齐；中文与数字混排时数字单独包裹，避免行高跳动。

### 4.3 间距与触控

- 基础间距单位 8rpx 倍数：`8 / 16 / 24 / 32 / 40 / 48`。
- 页面左右安全边距 32rpx；卡片内边距 24—32rpx；卡片间距 24rpx。
- **触控目标最小 88rpx × 88rpx**（约 44px，符合 iOS HIG 与微信设计指南）；行内文本按钮需外加不可见热区。
- 底部安全区：使用 `env(safe-area-inset-bottom)`，固定操作条不得遮挡内容。

### 4.4 组件规范（统一后各方案共用结构、各自取值）

| 组件 | 规范要点 |
|---|---|
| 卡片 | 仅用于"独立可重复项/框定工具"；不使用卡片套卡片；页面分区用整宽区块而非浮动卡片 |
| 按钮 | 主按钮（填充）、次按钮（描边）、危险按钮（描边红）、纯文本按钮（行内），最多 1 个主按钮/屏 |
| 输入框 | 高度 ≥ 88rpx；标签始终在输入框上方或左侧，不放占位符当标签；单位常驻显示 |
| 筛选器 | 周期/训练组/项目使用分段控件或下拉选择；已选条件以可关闭标签回显 |
| 导航 | 角色工作台使用底部导航（学生/教练）或顶部标签（数据密集页）；子页面使用返回 + 标题，不使用大标题 |
| 数据可视化 | 复用现有 `trend-chart` Canvas 组件（折线）；新增柱状/进度条使用纯 WXSS 实现，不引入图表库 |
| 加载态 | 骨架屏优先，过渡到内容；不使用"空白 + 转圈"占满首屏 |
| 空状态 | ≤ 2 行说明 + 1 个行动按钮，高度 ≤ 240rpx |
| 交互反馈 | 提交按钮 loading + 防重复点击；操作结果用轻提示；错误就地显示在字段旁 |
| 表单分组 | 每个分组 ≤ 5 个字段；长表单强制分组 + 折叠次要字段 |

### 4.5 文案规范（直接对应真机问题 4—7）

- 页面内**只使用中文业务名**，不再出现 `COACH / ATTENDANCE / STUDENT / STATISTICS` 等英文模块名。
- 角色文案必须跟随当前身份：developer 入口进入的页面显示"全局/管理"语义，不显示"教练端"。
- 页面顶部不再重复"大标题 + 长说明"：改为"页面标题（必要时带对象名）+ 可选的一行口径说明"。
- 技术性说明（权限校验、数据范围）下沉为：
  1. 首次进入的一次性提示，可关闭；
  2. 或详情/帮助浮层；
  3. 关键规则（如出勤率口径）改为中性说明样式，并置于数据旁，不用黄色警示块占据首屏。

## 5. 三套视觉方案设计理念

三套方案**使用同一份模拟数据、同一套页面结构清单**，但**布局范式、信息密度、导航方式与交互方式各不相同**，确保差异可感知，而不是换色。

### 方案 A1 · 专业竞技科技风（`A1-竞技科技/index.html`）

- **设计隐喻**：场馆大屏 / 教练指挥台。
- **视觉**：近黑场地底色、深蓝品牌面、竞技青与能量黄绿双强调色；卡片采用小圆角与左侧强调条；数值使用等宽大字号并带发光感。
- **布局范式**：**仪表盘 + 指挥队列**。学生首页是"PB 仪表盘 + 今日签到"；教练工作台是"KPI 条 + 待办队列 + 模块宫格"；统计页是"广播式图表 + 排行榜"。
- **交互差异**：底部固定导航；分段控件切换待办类型；行内按钮直接处理；表单使用"步骤条 + 折叠次要参数"。
- **适用取向**：竞技氛围最强，适合"训练日高频、看数据、要效率"的教练与有成就感诉求的学生。

### 方案 A2 · 现代运动品牌风（`A2-运动品牌/index.html`）

- **设计隐喻**：运动品牌 App（训练社区化、鼓励式）。
- **视觉**：明亮页面底、大圆角卡片、能量橙 + 乔格蓝 + 薄荷绿 + 日光黄；主色块 Hero 承载关键信息；环形进度与领奖台作为情绪符号。
- **布局范式**：**卡片叙事流**。学生首页是"问候 → 目标进度环 → 今日训练时间线 → 快捷入口 → 动态"；教练工作台是"今日动作 Hero → 待办指标 → 学员关注 → 常用功能"；统计页用领奖台呈现排行榜。
- **交互差异**：横向滑动胶囊入口；大号数字步进器；分步表单；底部悬浮胶囊导航。
- **适用取向**：亲和度与学生留存最好，适合把"坚持训练"作为产品情绪的取向。

### 方案 A3 · 极简专业数据风（`A3-极简数据/index.html`）

- **设计隐喻**：专业数据工具 / 报表工作台。
- **视觉**：纸白底、1px 细线分隔、几乎无阴影、小圆角；单一品牌蓝 + 数据语义色（正向绿/预警橙/危险红/说明青）；中文标签，无英文模块名。
- **布局范式**：**表格与字段组优先**。学生首页是"信息密度优先的指标网格 + 待办勾选 + 成绩表"；教练工作台是"收件箱式待办表 + 行内文本操作"；统计页是"指标网格 + 趋势 + 对比表 + 排名表"；表单是"横向字段组（标签在左、值在右）"。
- **交互差异**：**顶部标签式导航**（不使用底部导航），行内文本操作，字段级就地编辑，折叠 `<details>` 式次要参数。
- **适用取向**：同等屏幕信息量最大、单次操作步数最少，最接近"专业工具"，但情绪价值与品牌感较弱。

## 7. 三套方案对比评估

评分标准：1 分（弱）—5 分（强）。"页面复杂程度""实现难度""维护成本""性能影响"为**反向指标**，分数越高表示越好（即越简单/越易实现/成本越低/影响越小）。

| 评估维度 | A1 竞技科技 | A2 运动品牌 | A3 极简数据 |
|---|---|---|---|
| 视觉专业程度 | **5** | 4 | 4 |
| 运动竞技氛围 | **5** | 5 | 3 |
| 学生使用体验 | 4 | **5** | 3 |
| 教练操作效率 | 4 | 3 | **5** |
| 数据阅读体验 | 4 | 4 | **5** |
| 页面复杂程度（越高越简单） | 3 | 2 | **5** |
| 微信小程序实现难度（越高越易实现） | 3 | 3 | **5** |
| 维护成本（越高成本越低） | 3 | 3 | **5** |
| 性能影响（越高影响越小） | 4 | 3 | **5** |
| **合计（满分 45）** | 35 | 32 | **40** |

### 7.1 方案 A1 优缺点

- **优点**：竞技氛围与"专业体育产品"气质最强；数值表现力好；工作台"待办队列"结构清晰；深色底在 OLED 屏省电。
- **缺点**：深色方案对白底改造成本高（每个页面都要重做层级）；深色下错误/警示色可读性需逐一校准；长时间阅读表单易疲劳；表单类页面用深色不如浅色清爽；小程序 `wxss` 需要大量自定义状态样式；维护成本中高。

### 7.2 方案 A2 优缺点

- **优点**：学生端亲和度与留存情绪最好；目标进度环、领奖台等元素对"长期坚持"有正向作用；品牌感强，适合对外展示与家长期待。
- **缺点**：信息密度最低（实测统计页内容高度 1407px，超出首屏 607px）；卡片化过重，容易滑回"重复白卡片"的老问题；横向滑动胶囊与悬浮导航增加实现与维护成本；教练高频操作效率一般；单屏展示信息量不足，需要更多滚动。

### 7.3 方案 A3 优缺点

- **优点**：信息密度最高（A3 大量页面在单屏内完成，教练工作台整页 844px 内不需滚动）；教练操作效率与数据阅读体验最好；实现难度与维护成本最低（几乎全部可用现有 `wxss` 能力实现，无阴影/无渐变/无复杂动效）；性能影响最小。
- **缺点**：情绪价值与品牌感偏弱，学生端"想看进步"的激励感不足；纯表格风格对低龄学生吸引力较低；顶部标签导航在多角色场景下需要额外处理返回路径。

### 7.4 三套方案的共同改进（无论选哪套都建议采纳）

1. 删除页面顶部英文模块名与长说明，改为"对象名 + 一行口径"。
2. 三类工作台按"待办 → 常用 → 其余"重排，不做按钮平铺。
3. GPS 考勤改为地图选点，取消手动经纬度输入。
4. 训练计划表单按训练类型突出核心参数，其余折叠。
5. 赛事表单分为 5 组，组别改为可选标签，参赛项目多选加大命中区域。
6. 统计页具备指标 / 趋势 / 组间比较 / 排行榜 / 导出五要素，复用现有 Canvas 组件。
7. 通知突出重要通知；反馈突出"需要关注"学生。
8. 空状态与提示精简，技术说明下沉。

## 8. 推荐方案与理由

### 推荐：**以 A3 为骨架，融合 A1 的数据表现力与 A2 的学生情绪元素**

**推荐不是"三选一"，而是分层融合**，理由如下：

1. **场景差异客观存在，单一风格无法同时最优**。教练端高频、多字段、连续操作，需要 A3 的密度与效率；学生端低频、看结果、需要激励，需要 A2 的情绪表达；统计页需要 A1 的数据表现力。
2. **A3 的骨架能直接解决 8 个已确认问题**（信息密度、按钮堆叠、重复卡片、表单过长、空状态浪费、模板化布局、技术提示占位、操作步骤多），且实现成本与维护成本最低。
3. **A1 的"数值即主角"原则可以低成本嫁接**：仅在"关键指标、PB、排名、出勤率"四处使用大号等宽数字与强调色条，不需要把整站变深色。
4. **A2 的"目标进度环 + 领奖台"可以只用于学生首页与排行榜两处**，作为情绪点，不铺满全站，避免信息密度下降。

**具体融合建议**：

| 区域 | 取自 | 说明 |
|---|---|---|
| 全局设计令牌、表单、列表、表格、导航 | A3 | 纸白底、细线分隔、中文标签、横向字段组 |
| 三类角色工作台 | A3 结构 + A1 数据条 | 待办优先、KPI 条用等宽大数字 + 强调色 |
| 学生首页 | A2 情绪 + A3 密度 | 保留目标进度环与"连续训练"，其余用指标网格 |
| 数据统计页 | A1 表现力 + A3 表格 | 关键指标大号化 + 趋势图 + 对比表 + 排行榜 |
| 排行榜 / 领奖台 | A2 领奖台 | 仅作顶部 3 名的情绪呈现，第 4 名起回到表格 |
| 表单类页面 | A3 | 分组字段组 + 核心参数前置 + 次要参数折叠 |
| 动效 | 适度（1—2 处） | 仅签到成功、进度条增长，不做全站动效 |

**为什么不推荐纯 A2**：学生端体验最好，但教练端效率与信息密度不足，且卡片化设计容易重新滑向"重复白卡片"的既有问题，改造与维护成本最高。

**为什么不推荐纯 A1**：竞技气质最好，但深色改造涉及全部 28 个页面与所有表单状态，且长表单在深色下体验不佳，成本/收益比最低。

最终方案由项目所有者决定。**若只想要最省事、最稳的结果，选纯 A3；若最看重学生端留存，选 A2 或 A3+A2 融合；若最看重竞技氛围，选 A1 或 A3+A1 融合。**

### 11.1 微信平台配置与权限（已核对官方文档）

已核对官方文档（`wx.chooseLocation`、`map` 组件）确认：

1. **`wx.getLocation` / `wx.chooseLocation` 属于受限地理位置接口**
   - 需要用户授权 `scope.userLocation`；
   - 自 **2022-07-14** 后发布的小程序，必须在 `app.json` 中声明，否则接口无法正常使用（项目当前已声明 `"requiredPrivateInfos": ["getLocation"]`）；
   - **且需要在「小程序管理后台 → 开发 → 开发管理 → 接口设置」中自助开通该接口权限**，该接口"暂只针对具备与地理位置强相关的使用场景的小程序开放"；**代码审核环节会检测是否已开通，未开通将在提审环节被拦截**。
   - **因此：开通接口权限是必须由所有者在微信公众平台完成的配置步骤，无法由代码侧绕过。**

2. **`<map>` 组件本身不需要定位权限**
   - `map` 组件为基础组件（1.0.0 起支持），可用于展示地图与点击选点；仅 `show-location`（显示当前定位点）自 3.10.0 起需要位置授权——本项目不使用该属性。

3. **不引入付费地图能力**
   - 「地图个性化样式」自 **2023-06-29** 起需在微信公众平台付费管理购买后使用——**阶段7不采用**，原型中的地图为示意图形，正式实现使用默认样式。
   - 「地图服务 API」（POI 搜索、正/逆地址解析）需要腾讯位置服务 key 与配额——**阶段7不采用**。

4. **隐私保护指引**：需在微信公众平台的《用户隐私保护指引》中声明"位置信息"的收集目的（用于训练签到时判断是否在训练场地范围内），并在首次调用前完成隐私授权流程。这同样是平台侧配置。

**GPS 考勤的推荐实现路径（含降级）**

| 方案 | 依赖 | 体验 | 建议 |
|---|---|---|---|
| P1 首选 | `wx.chooseLocation`（需开通接口权限） | 打开微信内置地图，可搜索地点、返回地点名与经纬度 | 权限开通后使用；**不产生付费** |
| P2 保底（不依赖受限接口） | `<map>` 组件 + `bindtap` 取点 + `markers/circles` | 教练在页面地图上点选/拖动中心点，实时预览半径圈 | **无论 P1 是否开通都建议实现**，作为输入方式与容错 |
| P3 兜底 | 手动输入经纬度（现状） | 差 | 仅在 P1、P2 均不可用时保留，默认隐藏 |

**给所有者的平台配置清单（需在微信公众平台操作，阶段7实施前提供或确认）**

1. 「开发 → 开发管理 → 接口设置」→ 申请/开通「地理位置」接口权限（`getLocation`、`chooseLocation`）。

## 13. 阶段7建议验收标准

### 13.1 设计系统

1. 颜色、字号、间距、圆角、阴影全部来自 `app.wxss` 设计令牌，页面内无散落硬编码颜色（需保留例外清单并说明原因）。
2. 全站统一使用同一套页面头部、区块头、按钮、输入框、筛选器、空状态、加载态组件。
3. 单屏内主按钮不超过 1 个。

### 13.2 针对真机 20 项问题的逐条验收

| # | 原问题 | 验收方式 |
|---|---|---|
| 1 | developer 工作台按钮纵向堆叠 | 首屏为职责分组（≤4 组），无超过 4 个连续纵向按钮 |
| 2 | 工作台缺分组与待办 | 三类工作台首屏均含"待办/待处理"区，且待办可直接进入处理 |
| 3 | 三角色首页缺信息层级 | 首屏可见"最重要信息 + 主要动作"，无需滚动 |
| 4 | 重复英文模块名 | 全站搜索 `COACH / ATTENDANCE / STUDENT / STATISTICS / DEVELOPER` 等英文模块名，结果为 0（专业术语如 PB/RPE 除外） |
| 5 | developer 看到 COACH 字样 | developer 进入每个共享页面时角色文案为"全局/管理"，无"教练端"字样 |
| 6 | 顶部大标题 + 长说明 | 页面头部高度 ≤ 120rpx，且每个页面最多 1 行说明 |
| 7 | 黄色技术提示占空间 | 技术性说明数量下降 ≥70%，首屏无黄色警示块（业务性提示除外） |
| 8 | 白卡片按钮重复 | 统计/表单/列表页具备可区分的布局语言（非同一卡片样式） |
| 9 | 信息密度偏低 | 三类工作台首屏信息条数 ≥ 旧版 +50%；教练工作台整页无需滚动即可看到待办与今日考勤 |
| 10 | 页面缺差异化布局 | 驾驶舱 / 编辑器 / 收件箱 / 表格四类页面布局彼此可区分 |
| 11 | GPS 需手输经纬度 | 建场次流程中**不存在**手动经纬度输入框；经纬度只能由选点或定位产生 |
| 12 | GPS 表单缺字段说明 | 半径、精度阈值、签到窗口、迟到线均有字段说明文字 |
| 13 | 训练计划表单过长、类型无差异 | 选择"短跑专项"显示 距离/组数/次数/休息；选择"力量训练"显示 动作/组数/次数/负荷；其余参数默认折叠 |
| 14 | 赛事表单长、复选框拥挤 | 表单分为 5 组；项目多选命中区域 ≥88rpx；单屏可见组数与已选数量 |
| 15 | 组别靠文本输入 | 组别为可选标签/多选，不要求用户记住逗号分隔格式 |
| 16 | 统计页缺驾驶舱表现力 | 具备关键指标、趋势、训练组比较、排行榜、导出五要素，且复用现有 Canvas 组件 |
| 17 | 通知未突出重要 | 管理端与学生端均对重要通知有置顶 + 视觉区分 |
| 18 | 反馈未突出需关注学生 | 进入反馈页即可看到"需要关注"清单，无需逐条阅读 |
| 19 | 空状态占用过多空间 | 空状态高度 ≤240rpx，≤2 行说明 + 1 个行动按钮 |
| 20 | 体验仍像后台工具 | 由上述 1—19 综合判定；另需通过 13.3 与 13.4 |

### 13.3 可用性与可达性

4. 所有可点击元素触控目标 ≥ 88rpx（约 44px）。
