# 阶段2-D｜教练端PB成绩审核系统设计与测试记录

**日期：2026-10-13**
**状态：本地开发与自动化测试完成，云端未部署。**

## 1. 目标

建立高效、完整的运动成绩审核界面，让教练在少量操作步骤内完成：

- 查看本人负责训练组内学生的待审核成绩。
- 查看学生姓名、训练组、项目、成绩、单位、取得日期、来源和状态。
- 通过或驳回成绩，驳回必须填写审核意见。
- 审核后立即刷新列表并显示剩余待审核数量。

developer 保留既有全局审核权限；学生不能审核成绩。

## 2. 复用的后端接口

阶段2-A已实现以下接口，本阶段不重复创建：

### admin.list_pending_performances

- 允许角色：`developer`、`coach`。
- coach 仅返回本人负责训练组内学生的待审核成绩。
- developer 返回全局待审核成绩。
- 返回字段补充：`studentName`、`trainingGroupNames`、`note`、`pendingCount`、`truncated`。

### admin.review_performance

- 允许角色：`developer`、`coach`。
- 输入：`performanceId`、`decision`（`approve`/`reject`）、`comment`。
- 状态流转仅允许 `pending → approved` 或 `pending → rejected`。
- 事务内重新读取记录并检查状态，防止并发审核互相覆盖。
- 写入审核人、审核时间、审核意见、审核结果和审计日志。

## 3. 权限边界

- 角色和训练组范围全部由服务端根据可信微信身份计算。
- 前端不提交 `role`、`openid`、`reviewerUserId` 或训练组授权信息。
- 学生调用审核接口返回 `FORBIDDEN`。
- 教练跨训练组审核返回 `OUT_OF_SCOPE`，且事务不会开始。
- 停用账号返回 `ACCOUNT_DISABLED`。
- 已审核记录再次审核返回 `PERFORMANCE_NOT_PENDING`。

## 4. 并发审核

审核事务流程：

1. 事务内按 `performanceId` 读取最新记录。
2. 校验记录存在且 `status === 'pending'`。
3. 更新状态、审核人、审核时间和审核意见。
4. 写入对应审计日志。

两名审核者同时操作时，只有第一个事务成功；第二个事务在冲突重试后读到已变更状态并返回 `PERFORMANCE_NOT_PENDING`，不会覆盖审核结果。

## 5. 前端页面

页面：`pages/coach-performance-review/coach-performance-review`

功能：

- 待审核数量展示。
- 学生姓名与训练组。
- 体育专项、成绩数值、单位、取得日期、来源。
- 学生说明。
- 通过和驳回操作。
- 驳回意见编辑，未填写时阻止提交。
- 审核完成后刷新列表并提示结果。
- 重复提交防护：提交中禁用按钮并忽略重复点击。
- 空列表提示。
- 加载失败显示错误与重新加载。

入口：

- 教练工作台：`pages/coach/coach`。
- 开发者工作台：`pages/admin/admin`。

## 6. 学生端联动

- 学生提交成绩默认 `pending`。
- 只有 `approved` 成绩进入正式成绩曲线、正式PB、阶段变化和目标比较。
- `rejected` 成绩保留记录、审核状态和审核意见，不进入正式统计。
- 报告页面每次重新加载都会重新调用云函数，可获取最新审核结果。
- 没有 approved 成绩时，PB和趋势显示明确的空状态。
