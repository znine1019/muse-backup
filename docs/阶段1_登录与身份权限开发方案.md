# 阶段1｜微信登录与身份权限开发方案

**状态：本地代码已完成，等待云端部署和真实环境验证。**
本方案只覆盖 M01 的登录、待审核用户、角色授权和最小权限边界；具体字段、审批责任人及训练组绑定流程仍需用户确认。

## 1. 目标

1. 微信用户可建立待审核身份，但不会自动获得俱乐部内部权限。
2. 角色和教练管理范围由云函数根据可信微信身份判定。
3. 前端只负责交互和展示，不把页面隐藏作为安全措施。
4. 支持同一微信账号拥有多个已授权角色，但角色切换仍需服务端返回的授权结果支撑。
5. 所有关键授权和审核操作可审计、可重复提交且不会产生重复账号。

## 2. 身份与状态模型

### 账号状态

`pending_profile` → `pending_review` → `active`／`rejected`／`disabled`

- `pending_profile`：微信身份已建立，但学生档案未提交。
- `pending_review`：档案已提交，等待管理员或授权教练审核。
- `active`：已通过审核并能访问已授权角色。
- `rejected`：审核未通过，保留必要处理结果。
- `disabled`：账号被停用，即使原有角色也不能访问内部数据。

### 角色

- `student`：只能访问本人数据和被允许展示的内部榜单。
- `coach`：只能访问被分配训练组或学生范围内的数据。
- `admin`：用于账号、角色、配置和审计管理；必须是少量明确授权账号。

角色授权记录需要保存授权人、授权时间、状态和必要的撤销信息。前端可显示角色切换入口，但最终能力集合由云函数返回。

## 3. 可信登录流程

1. 云环境 ID 确认后，小程序启动时初始化微信云开发。
2. 前端调用登录云函数，不传递可信身份字段。
3. 云函数从微信云开发调用上下文读取 `OPENID`／`UNIONID`。
4. 云函数按 OpenID 查询内部用户：
   - 不存在：创建 `pending_profile` 账号。
   - 已存在：返回账号状态和已授权角色。
   - 已停用：返回不可访问状态，不返回内部数据。
5. 学生填写最小必要档案后提交审核，状态变为 `pending_review`。
6. 授权审核人通过独立云函数处理，成功后写入角色授权和审计日志。
7. 前端刷新会话能力；不得只依赖本地缓存角色。

## 4. 云函数接口草案

所有写操作先经过统一的 `withTrustedIdentity` 中间层，统一完成身份读取、账号状态检查、角色检查、范围检查、参数校验和审计。

| 云函数接口 | 调用者 | 核心职责 |
|---|---|---|
| `auth_login` | 任意微信用户 | 根据可信 OpenID 创建或读取账号，返回最小会话信息 |
| `profile_get` | 已登录用户 | 只返回本人或授权范围内的档案字段 |
| `profile_submit` | 学生 | 创建／更新待审核档案，禁止提交角色和审批状态 |
| `admin_list_pending_users` | 管理员 | 分页查看待审核账号，只返回审核必要字段 |
| `admin_review_user` | 管理员或获授权教练 | 通过或拒绝注册，记录审核人、时间和意见 |
| `admin_assign_role` | 管理员 | 授予或撤销角色，校验初始管理员授权链 |
| `admin_set_data_scope` | 管理员 | 配置教练员负责的训练组或学生范围 |
| `auth_get_capabilities` | 已登录用户 | 返回服务端计算后的角色与能力集合 |

接口名称只是开发草案，阶段1实现前需要再次评审。所有接口必须验证参数类型、集合归属和调用者权限。

## 5. 数据库最小草案

| 集合 | 关键字段草案 | 访问原则 |
|---|---|---|
| `users` | `_openid`、`status`、`roles`、`created_at`、`updated_at` | 仅云函数访问，客户端不能任意改角色和状态 |
| `student_profiles` | `user_id`、必要基础资料、`review_status` | 学生只能提交本人数据，读取受服务端范围限制 |
| `coaches` | `user_id`、`enabled` | 仅管理端维护 |
| `training_groups` | `name`、`enabled`、`coach_ids` | 分组字段待用户确认后定型 |
| `group_memberships` | `group_id`、`user_id`、`role_in_group` | 用于计算服务端数据范围 |
| `audit_logs` | `actor_user_id`、`action`、`target_id`、`result`、`created_at` | 只追加，不返回敏感明细 |

不在本阶段采集伤病、身份证、定位轨迹或赛事证明等敏感信息。

## 6. 权限检查规则

1. 禁止从前端接受 `OpenID`、`role`、`isAdmin` 或审批结果作为授权依据。
2. 管理员权限必须来自服务端角色记录和启用状态。
3. 教练员查询学生时，先验证学生是否属于其负责范围。
4. 学生读取任何记录时，先验证记录的学生归属为本人。
5. 拒绝、停用和撤销权限后，下一次服务端请求立即生效；不能长期依赖本地缓存。
6. 重复点击登录或审核必须幂等，不产生重复账号或重复授权记录。
7. 授权、驳回、停用、角色变更和范围变更必须写审计日志。
8. 返回值按页面最小需要裁剪，不返回整条内部账号记录。

## 7. 前端页面范围

阶段1只新增以下页面或状态，不提前开展其他业务：

- 登录／会话初始化状态页。
- 首次资料提交页。
- 待审核、已拒绝、已停用状态页。
- 角色选择页，仅在服务端返回多个已授权角色时显示。
- 学生端最小主页。
- 教练员端最小工作台。
- 管理员最小账号审核与角色授权入口。

现有学生、教练员、开发者页面均通过云函数会话和 action 级权限校验；页面显示不作为正式权限依据。

## 8. 必备测试

- 无会话访问受保护接口应被拒绝。
- 待审核账号不能读取内部数据。
- 已停用账号不能继续使用旧角色。
- 学生不能通过修改 `studentId` 读取他人档案。
- 教练员不能查询非负责训练组的数据。
- 普通用户调用管理员接口应被拒绝。
- 多角色账号只获得当前服务端允许的能力。
- 重复登录、重复提交档案和重复审核保持幂等。
- 审计日志能追踪授权、撤销和驳回。

测试使用完全虚构数据，不使用真实学生个人信息。

## 9. 开工前需要确认

1. 首个管理员账号如何安全初始化，不能由前端自行选择管理员。
2. 学生提交审核后由谁审核、审核失败如何修改。
3. 教练员与训练组／学生范围的录入责任人。
4. 学生注册档案在阶段1实际采集的最小字段。
5. 账号停用、角色撤销和重复账号处理规则。
6. 开发、体验、正式环境及云开发预算。

这些问题确认后再创建数据库集合和云函数，不能由开发工具擅自补成最终业务规则。
