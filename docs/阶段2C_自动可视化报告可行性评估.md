# 阶段2-C｜学生身体指标与运动成绩自动可视化报告可行性评估

**评估日期：2026-10-13**  
**结论：B. 需要适度调整后加入 V1.6。**

现有数据结构和轻量原生图表方案足以支持 V1.6 基础报告；主要调整是增加只读统计接口，并为“当前成绩与体考目标数值对比”补充结构化目标字段。无需大规模重构、外部仪器或付费服务。

## 1. 现有数据能力

### body_measurements

当前字段：

- `userId`
- `heightCm`
- `weightKg`
- `measuredAt`
- `source`
- `submittedBy`
- `createdAt`
- `schemaVersion`
- 默认 `_id_`、`_openid_1` 和 `idx_body_measurements_user_measured_at`

可支持：

- 身高/体重历史。
- 按测量日期排序。
- 测量次数不足提示。
- 最新一次测量和学生档案当前值同步。

### performance_records

当前字段：

- `studentUserId`
- `eventCode`
- `eventName`
- `value`
- `unit`
- `comparison`
- `achievedAt`
- `source`
- `status`
- `reviewedBy`
- `reviewedAt`
- `reviewComment`
- `createdAt`、`updatedAt`
- 两个业务组合索引

可支持：

- 按项目筛选正式成绩。
- approved成绩曲线。
- 个人最好成绩计算。
- 阶段变化幅度计算。
- 计时/距离/高度不同比较方向。

## 2. 数据结构结论

### 现有集合是否足够

V1.6基础报告无需新增集合。

- 身高趋势：使用 `body_measurements.heightCm`。
- 体重趋势：使用 `body_measurements.weightKg`。
- 正式成绩趋势：使用 `performance_records.status=approved`。
- 正式PB：对 approved 记录按项目比较规则取最优值。
- 阶段变化：比较最早与最新正式成绩，或用户选定的时间范围。
- 训练项目切换：使用 `eventCode`。

### 是否需要修改字段

不需要数据库结构迁移，但建议增加一个可选档案字段：

- `examGoal.targetEventCode`
- `examGoal.targetValue`

原因：当前 `examGoal.targetScore` 是自由文本，例如“100米 12秒”，无法可靠地和服务端数值成绩比较。加入后可在现有 `student_profiles` 文档中直接保存，不需要新集合。

当前 `student_profiles` 暂无学生业务数据，因此不存在历史数据迁移压力。未增加数值目标时，V1.6只展示文字目标，不做数值对比。

## 3. API评估

现有接口：

- `profile.list_measurements`：可读取本人最多100条身体记录。
- `performance.list_mine`：可读取本人最多100条成绩记录，包含pending/approved/rejected。
- `admin.get_student_profile`：教练/开发者读取档案，但身体和成绩各只返回最近20条。

不足以直接形成完整历史报告，因此建议新增只读接口：

### report.get_my_report

仅当前学生调用，服务端固定使用可信微信身份映射本人，不接受目标用户ID。

### admin.get_student_report

仅教练/开发者调用：

- developer可查看全部学生。
- coach只能查看本人负责训练组内学生。
- 复用现有 membership 范围校验。

建议返回：

- 身高序列：日期、cm。
- 体重序列：日期、kg。
- 项目列表：项目、单位、比较方向。
- 选定项目的 approved 成绩序列。
- 正式PB。
- 数值目标及差值（存在结构化目标时）。
- 阶段变化幅度和数据点数量。
- `hasEnoughData` 等数据质量标记。

正式成绩接口不得返回 pending/rejected 作为曲线数据。

## 4. 图表技术方案

推荐使用微信小程序原生 Canvas 2D：

- 基础库 `3.17.4`，满足 `<canvas type="2d">` 要求。
- 项目当前没有图表依赖。
- 原生 Canvas 可绘制坐标轴、折线、散点、目标线和数据不足提示。
- 无需引入 ECharts、F2 或外部CDN。
- 不增加云函数依赖，不产生额外服务费用。

推荐实现：

1. 单独封装轻量 `trend-chart` 组件。
2. 身高和体重分别使用独立坐标轴和单位，不混合量纲。
3. 成绩图按当前 `eventCode` 自动采用升序或降序视觉提示。
4. 只有1个数据点时显示当前值，不绘制虚假趋势线。
5. 无数据或数据不足时显示明确提示。
6. 原生Canvas不可用时保留表格数据作为降级展示。

## 5. 页面建议

### 学生端

新增 `pages/student-report/student-report`：

- 身高趋势。
- 体重趋势。
- 项目选择器。
- approved成绩趋势。
- 正式PB卡片。
- 体考目标对比。
- 阶段变化幅度。

学生页增加“运动报告”入口。

### 教练/开发者

扩展现有 `pages/profile-view/profile-view`：

- 增加“查看运动报告”入口。
- 传入学生ID后使用 `admin.get_student_report`。
- 页面展示与学生端一致，但数据范围由服务端权限决定。

## 6. 权限与安全

- 学生报告接口只使用服务端可信身份。
- 学生不能通过修改 `targetUserId` 读取他人报告。
- coach访问前校验训练组范围。
- developer沿用全局权限。
- 不开放数据库客户端直读。
- 不绕过成绩审核状态。
- 不返回未授权学生的数据。

## 7. 性能与成本

单次报告预计：

- 1次档案读取。
- 1次身体记录查询，最多约100至200条。
- 1次成绩记录查询，最多约100至300条。

按现有300名学生规模和低并发使用，读取量和云函数运行时间增加较小，不需要新的付费资源。可在前端会话内缓存最近一次报告，减少重复加载。

现有索引可覆盖学生本人身体和成绩历史查询。若未来增加多学生、多项目复杂统计，V1.7可再评估增加 `studentUserId + eventCode + status + achievedAt` 复合索引，本阶段无需修改。

## 8. V1.6 / V1.7划分

### 建议纳入V1.6

- 身高趋势图。
- 体重趋势图。
- 正式PB展示。
- 按项目切换的approved成绩趋势图。
- 数值化体考目标对比（需要结构化目标字段）。
- 阶段成绩变化幅度。
- 数据不足和无数据提示。
- 学生本人和授权教练查看。

### 建议放入V1.7

- 多维运动能力雷达图。
- 综合专项能力评分。
- 专业体测报告。
- 体脂率、肌肉量等未采集指标。
- 体测报告导出（仅使用系统内已录入数据）。
- 复杂报告导出。

### 永久排除范围

- 第三方体测仪器API或SDK对接。
- 蓝牙、串口、厂商云平台或其他设备连接。
- 仪器数据自动导入。
- 将设备对接作为报告功能前置条件。
- 任何未由系统实际保存的数据生成分析。

## 9. 推荐实施顺序

1. 确认新增 `examGoal.targetEventCode` 和 `examGoal.targetValue` 的本地字段方案。
2. 新增只读报告接口和学生/管理员权限分支。
3. 增加Native Canvas图表组件。
4. 新增学生运动报告页并接入现有档案查看页。
5. 补充接口、权限、数值比较、空数据和图表数据转换测试。
6. 后续按阶段T制度使用真实student/coach账号集中验收。

## 10. 结论

**B. 需要适度调整后加入V1.6。**

没有大规模数据库重构、复杂统计模型或付费服务需求。第三方体测仪器API、SDK、设备连接和自动导入已从V1.6、V1.7及后续版本中永久排除。现有两个集合足够，增加一个轻量只读报告接口、结构化体考目标字段和原生Canvas页面即可实现V1.6基础报告。

## 11. 本地实现完成记录（2026-10-13）

### 11.1 报告接口

- `report.get_my_report`：只使用服务端可信身份，学生只读取本人报告。
- `admin.get_student_report`：教练仅可读取负责训练组内学生，developer 保留全局读取权限。
- 报告返回身高/体重趋势、approved成绩趋势、正式PB、阶段变化、结构化体考目标比较和数据质量标记。

### 11.2 历史数据完整性

- 成绩历史使用 `count()` 获取总数，再以 `achievedAt asc, _id asc` 稳定排序分页读取，按 `_id` 去重并校验最终数量。
- 身体指标历史使用 `measuredAt asc, _id asc` 稳定排序分页读取，并进行相同的完整性校验。
- 任一来源读取不完整时报错 `REPORT_INCOMPLETE`，不返回可能错误的正式PB。
- 图表使用独立的 `CHART_POINT_LIMIT = 120`，正式PB、最近成绩、阶段变化和目标比较始终基于完整历史。

### 11.3 Canvas与页面

- `trend-chart` 使用原生 Canvas 2D，处理设备像素比、空数据、单数据点和多数据点趋势。
- 仅有一条记录时显示当前数值和“暂无足够历史数据形成趋势”，不伪造第二个点。
- 折线图绘制首/中/末关键日期标签，避免小屏幕全量标注。
- 学生报告页提供重新加载；重新获取失败或切换学生时清空旧数据，不跨用户显示缓存。

### 11.4 尚未完成的验证

- 微信真机 Canvas 视觉效果、不同机型像素比与滚动性能。
- 云端部署后的真实数据库读写与报告接口基础验证。
- 真实学生/教练账号的阶段T综合验收。
- 若未来单学生成绩规模显著增长，建议评估 `performance_records` 的 `studentUserId:1, status:1, achievedAt:1` 索引；本轮未修改云端索引。

## 12. 本地演示预览（2026-10-13）

- 目标：在云端无真实学生身体指标和成绩时，让现有developer账号在微信开发者工具预览与iPhone预览中检查报告视觉、内容组织、图表与手机端体验。
- 演示数据：本地模块 `miniprogram/demo/sport-report-demo.js`，包含虚构学生档案、6条身高与体重记录、100米4条、800米3条、跳远3条成绩、正式PB、阶段变化、结构化体考目标和目标差距。
- 入口：开发者工作台“预览运动数据报告（DEMO）”，跳转到 `pages/student-report/student-report?demo=1`。
- 环境门禁：仅 `develop` 与 `trial` 允许；`release` 隐藏入口并忽略手工参数；演示模式还需 developer 会话。
- 隔离：不调用正式报告API、不写云数据库、不创建成绩、不修改PB与排行榜；演示页面明确标注“DEMO｜虚构演示数据”和“仅用于界面预览，不代表真实训练成绩”。
- 复用：继续使用 `student-report` 页面与 `trend-chart` Canvas组件，未重复开发图表系统；新增个人运动数据概览卡与长时项目时钟格式展示。
