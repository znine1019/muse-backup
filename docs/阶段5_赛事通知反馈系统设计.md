# 阶段5｜赛事、通知与训练反馈系统设计

**日期：2026-10-13**
**状态：本地开发与自动化测试阶段；本轮未创建云端集合、索引或部署云函数。**

## 1. 范围

阶段5包含三个相互关联但独立授权的业务域：

1. 赛事意向管理与名单汇总（M12）。
2. 俱乐部站内通知与已读状态（M08）。
3. 学生训练反馈与教练评价（M07）。

阶段5保留并复用阶段1至阶段4的身份、训练组、成绩目录、考勤和审计能力。第三方体测仪器、设备SDK/API、自动导入仪器数据不在V1.6、V1.7或后续版本规划中。

赛事模块的产品边界是“收集学生参赛意向、核对资料、记录教练办理进度和导出名单工具”。它不是赛事主办方报名系统，不自动向外部平台提交，不保存赛事平台密码。“官方报名已提交”只代表教练已在外部官方渠道完成操作，不代表主办方审核通过或学生已取得参赛资格。

## 2. 数据模型

阶段5拟新增以下五个集合，全部采用服务端访问、客户端不直接读写，云端权限建议为 `ADMINONLY`。本轮仅在本地代码中定义契约，尚未创建云端集合。

### 2.1 `competitions`

赛事主记录。

| 字段 | 类型 | 说明 |
|---|---|---|
| `competitionId` | string | 确定性业务ID，同时作为文档 `_id` |
| `title` | string | 赛事名称 |
| `description` | string | 赛事介绍 |
| `location` | string | 举办地点 |
| `eventDate` | date-only string | 比赛日期，`YYYY-MM-DD` |
| `registrationStartAt` | datetime string | 报名意向开始，`YYYY-MM-DD HH:mm` |
| `registrationEndAt` | datetime string | 报名意向截止，`YYYY-MM-DD HH:mm` |
| `requirements` | string | 报名要求 |
| `notes` | string | 教练内部备注 |
| `events` | array | 项目代码、名称、单位和组别 |
| `trainingGroupIds` | array | 可见训练组；developer 可创建全体可见记录 |
| `capacityEnabled` | boolean | 是否启用意向人数上限 |
| `capacity` | number/null | 可选上限，校验范围 1—100 |
| `activeStudentCount` | number | 当前有效意向的学生数，按学生级计数 |
| `status` | string | `draft`、`published`、`closed`、`archived` |
| `version` | number | 乐观锁版本 |
| `createdBy` | string | 创建者用户ID |
| `createdAt` | Date | 创建时间 |
| `updatedAt` | Date | 更新时间 |
| `schemaVersion` | number | 本地数据契约版本 |

`phase` 不持久化，由服务端按状态和当前UTC+8时间实时计算：`draft`、`not_started`、`open`、`closed`、`archived`。

人数规则：默认不限人数；启用上限时，同一学生在同一赛事的多个项目只按一个学生计入 `activeStudentCount`，项目数量独立统计。容量检查在事务内再次执行，避免并发突破上限。

| `reviewNote` | string | 教练处理说明 |
| `reviewedBy` | string | 教练用户ID |
| `reviewedAt` | Date | 最近处理时间 |
| `statusHistory` | array | 状态历史、操作者、时间和备注 |
| `version` | number | 办理状态乐观锁 |

| `comment` | string | 学生文字反馈 |

| `coachCommentBy` | string | 评价教练用户ID |
| `coachCommentAt` | Date/null | 评价时间 |

“需要关注”不持久化，由服务端按未完成、RPE较高或反馈文本包含风险提示计算。

## 3. 确定性ID与并发保护

- 赛事：`competitionIdForRequest(actorUserId, clientRequestId)`。
- 学生赛事意向：`registrationIdForStudentCompetition(studentUserId, competitionId)`，同赛事多项目合并到一条意向记录。
- 通知：`noticeIdForRequest(actorUserId, clientRequestId)`。
- 通知已读：`noticeReadId(noticeId, studentUserId)`。
- 训练反馈：`feedbackIdForStudentSession(studentUserId, sessionId)`。

所有写入使用 `doc(id).set()` 时，数据对象不再重复携带 `_id`。赛事、通知、报名意向、反馈和教练评价分别使用版本或事务内状态复查，避免并发覆盖；容量检查和人数调整在事务中完成。

## 4. 权限与服务端边界

- `competition.list_student`、`competition.submit_intent`、`competition.cancel_intent` 只接受学生角色；学生身份取自信任微信上下文，不接受客户端提交的学生ID。
- 赛事、通知管理动作只接受 coach 或 developer；coach 只能操作本人负责训练组的记录，developer 按现有规则全局查看。
- `notice.list_student`、`notice.get_student_detail`、`notice.mark_read` 只返回学生有效训练组可见的已发布通知。
- `feedback.list_eligible_sessions`、`feedback.submit`、`feedback.update` 只接受学生角色；必须存在已签到或迟到的本人考勤记录。
- `feedback.list_manage`、`feedback.review` 只接受 coach 或 developer；coach 只能查看/评价本人负责训练组学生。
- 所有前端页面只是调用正式 `api` 服务端动作；客户端角色、训练组、学生ID和办理状态都不是权限依据。
- 所有数据库读取通过现有仓储层完成，前端不直接访问业务集合。

## 5. 赛事流程

1. 教练或 developer 创建赛事草稿，选择项目、组别和可见训练组。
2. 发布后，学生在开放时间窗口内提交项目意向和补充说明。
3. 同一学生的多个项目合并为一条意向记录，赛事人数仍按学生计一人。
4. 教练在 `submitted`、`processing`、`registered`、`failed` 之间更新办理进度。
5. 教练可导出真实XLSX名单，用于在赛事官方渠道办理正式报名。
6. `registered` 后学生不能在系统内修改或取消，避免与外部正式报名状态冲突。
7. 关闭或归档赛事保留历史记录，不删除报名意向。

## 6. 通知流程

1. 教练或 developer 创建草稿并选择分类、重要程度和可见训练组。
2. 草稿发布后，学生端只看到已发布通知；重要通知置顶，普通通知按发布时间排序。
3. 学生可查看详情并标记已读，重复标记保持幂等。
4. 撤回后学生不再可见，归档保留管理历史。
5. 通知正文只存文本，不在普通日志输出学生个人信息。

## 7. 训练反馈流程

1. 学生只对近30天内已签到或迟到的场次填写反馈。
2. 未签到、请假或没有真实到训记录不能生成默认反馈。
3. 学生可查看本人历史反馈；提交和更新使用版本保护。
4. 教练在授权训练组范围内查看反馈，对需要关注的记录添加或更新评价。
5. 教练评价使用独立 `coachCommentVersion`，避免并发评价互相覆盖。
6. 反馈和评价不改变考勤事实，也不伪造训练完成情况。

## 8. XLSX导出

`miniprogram/utils/xlsx-writer.js` 在本地生成真实ZIP结构的 `.xlsx` 文件，包含 [Content_Types].xml、关系文件、workbook、worksheet 和 XML 转义。不使用CSV改名冒充XLSX，不引入第三方付费依赖。云端部署后仍应在服务端权限边界内生成或校验导出数据。

## 11. 自动化测试

阶段5测试覆盖：

- 赛事创建、发布、关闭、归档和版本冲突。
- 学生多项目意向合并、学生级人数上限、并发上限和取消。
- 训练组权限隔离、developer全局导出和禁用账号。
- 通知草稿、发布、撤回、归档、可见组、重要程度排序和幂等已读。
- 训练反馈必须基于真实签到/迟到，提交幂等、学生更新版本保护和教练评价并发保护。
- 真实ZIP/XLSX结构、XML转义和列名。
- 六个阶段5页面路由、入口、加载失败、表单提交、标记已读、反馈评价和XLSX导出。

本轮全部使用虚构数据和服务端内存仓储；不得将Mock测试描述为真实微信端验收。
